**📖 Documentation**

---

**CQOx（シーキューオーエックス）** は、  
マーケティング施策の **因果効果** と **利益・リスク・公平性** を一枚のコンソールにまとめるためのプラットフォームです。

- 生のイベントデータ（CSV やテーブル抽出）から  
  **インクリメンタル利益（Δ¥）** と **リスク** を推定し、
- 「実行すべき施策（Go）」「慎重にテストすべき施策（Canary）」「止めるべき施策（Hold）」を提示し、
- その裏側で **因果推論・実験・ポートフォリオ最適化・ガバナンス（公平性や頻度上限）** を自動で回します。

## 📊 システム概要

CQOx は、生データを因果推論・実験・ポートフォリオ最適化・ガバナンスの高度なパイプラインで処理し、実用的なインサイトに変換する包括的な因果マーケティング意思決定プラットフォームです。

**主要コンポーネント:**

- **フロントエンド (ポート 3004)**: React SPA + TanStack Query による状態管理
- **API ゲートウェイ (ポート 8000)**: FastAPI + JWT 認証 + RBAC
- **因果エンジン**: すべての統計推定器と診断機能をホストする Python サービス
- **リバースプロキシ (Nginx)**: トラフィックルーティング、SSL、WebSocket/SSE 対応
- **データベース**: PostgreSQL with Row-Level Security (RLS) によるマルチテナント対応
- **監視**: Prometheus (ポート 9090) + Grafana (ポート 3000)

## 1. なぜ CQOx が必要か

多くのツールはここで止まります：

- **見た目のダッシュボード**：CVR、売上、開封率など「起きたこと」のグラフ
- **ブラックボックスなスコア**：「購入確率 0.83」などの機械学習スコア

しかし、経営・マーケの現場で本当に聞かれるのは次のような問いです。

- 「このセグメントに、この施策を打ったとき、  
  **どれだけ利益が増えた（Δ¥）と言えるのか？**」
- 「どれくらいの **リスク** を取っているのか？最悪どこまで赤字になりうるのか？」
- 「この施策ポートフォリオで、  
  予算・リスク・公平性の制約を守りながら、成長を最大化できているか？」

Google / Meta / Netflix / Amazon、そして WPP / BCG / Accenture などのコンサルは、  
社内で次の 4 つを組み合わせたスタックを持っています。

1. **因果推論**（uplift、DiD、IV、RD、SCM など）
2. **実験プラットフォーム**（A/B テスト、多腕バンディット）
3. **ポートフォリオ最適化**（利益 vs リスク、CVaR）
4. **ガバナンス**（公平性・頻度キャップ・品質ゲート）

CQOx は、これらのパターンを 1 つのプロダクトにまとめたものです。

## 2. CSV から意思決定までのストーリー

典型的な利用フローはこうなります。

1. **データをアップロード**  
   - 例：キャンペーンログ、ユーザ単位の成果、属性、コスト情報

2. **因果デザインの設定（Causal Design）**  
   - アップロードしたカラムから、  
     **処置列（treatment）・成果列（outcome）・ユーザ ID・時間・チャネル・コスト** 候補を自動検知
   - ユーザが画面上で最終的な列を確認・修正
   - 使用する推定器（DR, IPW, DiD, IV, CF, SCM, RD など）を選択

3. **因果モデルの学習と診断**  
   - 複数の推定器を並列に学習し、  
     オーバーラップ・バランス・感度分析を実行
   - その結果をまとめて **Causal Assurance Score (CAS)** としてスコアリング

4. **Decision Console – マーケ意思決定コンソール**  
   - 実行候補の施策（Policy）を集約し、  
     期間内の **総インクリメンタル利益（Δ¥）・平均 Δ¥ / 施策・平均 CAS・テイルリスク(CVaR)** を一枚で表示
   - セグメント別・チャネル別に Drill-down 可能

5. **Portfolio – ポートフォリオ最適化 & ROI**  
   - 各施策を **利益 vs リスク vs CAS** の多目的パレートフロンティア上にプロット
   - 「どの施策をポートフォリオに含めるべきか」を提案

6. **Digital Twin – 顧客デジタルツイン**  
   - ペルソナごとに、プレミアム施策 / 値引き / ナーチャリング / リテンション施策を当てた場合の  
     反応と Δ¥ をシミュレーション

7. **Experiment Studio – オンライン・マルチアーム実験**  
   - 実際のトラフィックを使ったオンライン実験（A/B, 多腕バンディット）の設計・運用
   - 過去データを使ったマルチアーム因果分析

8. **Governance Center – 公平性・品質・コンプライアンス**  
   - 性別・年齢などの **センシティブ属性ごとの Δ¥ 差** をチェック
   - uplift 入力データの品質検査
   - **頻度キャップ・露出上限** の違反を検出し、ログを記録

9. **Export Gate**  
   - 承認されたセグメントや施策ポリシーを、  
     外部の ESP / CDP / マーケ自動化ツールにエクスポート

## 3. CQOx は何が違うのか

### 3.1 BI ダッシュボードとの違い

- BI は「起きたこと（売上、CVR）」をきれいに見せるツールです。
- CQOx は「施策を打った **結果として** どれだけ変わったか（Δ¥）」を推定し、  
  さらに「もし施策を変えたらどう変わりそうか」をシミュレーションします。

ポイント：

- すべてのビューの中心が **インクリメンタル利益（Δ¥）**  
  純売上ではなく「やったから増えた分」だけを見る。
- **施策単位（Policy 単位）** での分析が基本  
  （例：「App 有りの RFM4–5 に Push V3 を 3 通送る」など）
- すべての数字に **CAS（因果保証スコア）** と **リスク指標** が紐づく

### 3.2 一般的な AI / 機械学習ツールとの違い

よくある「AI マーケ支援ツール」は次のような動きをします。

- 「購入確率」「離脱確率」などの **予測モデル** を作る
- **AUC や logloss** など、統計的な損失関数を最小化するように学習する
- 予測スコアをそのまま「スコアが高い人＝狙い目」と解釈する

これに対して、CQOx は性質がまったく違います。

- **予測ではなく「もし〜していなかったら？」を扱う（因果）**  
  - AI は「今の情報を見て、この人は買いそうか？」という **予測** をします。  
  - CQOx は「この人に施策を送った場合と、送らなかった場合で、  
    **どれだけ売上が変わるか？**」という **反事実（カウンターファクト）** を推定します。  
  - そのために、推定器・仮定・診断がすべて明示されています。

- **指標は AUC ではなく、利益・リスク・公平性**  
  - 目的は「Δ¥ を最大化しつつ、リスクと不公平性を抑える」ことです。  
  - クリック数や CVR が上がっても、**増分利益がマイナス** なら「悪い施策」と判断されます。

- **ブラックボックスではなく、監査可能な仕組み**  
  - DR / IPW / DiD / IV / CF / SCM / RD などの推定器が UI から見えます。  
  - バランスチェック・オーバーラップ・感度分析も画面で確認できます。  
  - 「なぜこの施策が Go 判定なのか？」を、データサイエンティストがトレースできます。

- **時間が経っても壊れにくい**  
  - 単純な予測モデルは、データ分布が変わるとすぐ壊れます。  
  - CQOx は「施策の効果」を推定しているため、  
    特定のチャネルやセグメントが多少変化しても、**方針（ポリシー）自体は比較的安定** しやすい設計です。

一言でまとめると：

> 一般的な AI は「パターンを当てる」のが得意。  
> CQOx は「施策の **影響** を推定し、  
> その結果を利益とリスクの観点で **意思決定に落とし込む**」ことに特化しています。

### 3.3 uplift SaaS / コンサルティングとの違い

- コンサルティングファームは、  
  「一度きりの分析結果をまとめたスライド（戦略提案書）」を提供することが多いです。  
  CQOx は、これを **毎週 / 毎日回せる “コンソール” として常設** します。

- uplift 専用 SaaS は、スコアリングまでは強い一方で、  
  ポートフォリオ・ガバナンス・実験プラットフォームまでは踏み込まないことが多いです。  
  CQOx はこれらを **一つのワークフローに統合** している点が違います。

### 3.4 CQOx は AI をどう使い、何を任せないのか

CQOx 自体は「全部を AI に丸投げするツール」ではありません。  
AI（特に大規模言語モデル）は **サポート役** にとどめ、  
**意思決定の根拠は必ず因果推論とルール（ガバナンス）側に保持** します。

AI を使うのは、たとえばこんな場面です。

- ポートフォリオの推奨結果を、人が読みやすい文章で要約する  
  （例：「この 5 施策を採用すると、Δ¥ は約 66 万円、リスクは中程度、CAS は 0.75 です…」）
- セグメント説明やペルソナ説明文を自動生成する  
- Diagnostics の結果を「どこに注意すべきか」ハイライトする

逆に、AI に **任せない** のは次の部分です。

- 因果効果の推定そのもの（これは統計・因果推論のエンジンが担当）
- ガバナンスルール（公平性・頻度キャップ・品質ゲート）の判定
- 人間による最終承認なしに、勝手に施策を配信すること

この設計により、

- 「AI がなぜこう判断したのかわからない」状態を避けられ、
- 監査・再現性・コンプライアンスに耐えられる形で
  AI の便利さだけを取り込むことができます。

### 3.5 CQOx は何が違うのか：比較分析

以下の表は、CQOx とマーケティング意思決定の代替手法を比較したものです：

| **観点** | **従来型 BI ダッシュボード** | **一般的な AI/ML ツール** | **アップリフト SaaS** | **コンサルティングファーム** | **CQOx** |
|---------|---------------------------|----------------------|---------------------|---------------------------|---------|
| **主な焦点** | 記述的分析（何が起きたか） | 予測モデル（誰がコンバートするか） | アップリフトスコアリング | 戦略的調査（1回限り） | 因果的意思決定（次に何をすべきか） |
| **指標** | 売上、CVR、CTR | 購買確率、AUC | アップリフトスコア | カスタム KPI | インクリメンタル利益（Δ¥）、CAS、CVaR |
| **因果性** | なし – 相関のみ | 間接的（予測 ≠ 因果） | あり – アップリフトモデリング | あり – しかしアドホック | あり – 診断付き複数推定器 |
| **推定器** | なし | ML 分類器（XGBoost、NN） | DR、S-Learner、T-Learner | プロジェクトにより異なる | DR、IPW、DiD、IV、CF、SCM、RD |
| **ポートフォリオ最適化** | なし | なし | 限定的 | 手作業 / スプレッドシート | 自動パレート・フロンティア分析 |
| **デジタルツイン** | なし | なし | なし | まれ | あり – ペルソナレベルシミュレーション |
| **実験プラットフォーム** | なし | なし | 限定的 | なし | 完全 A/B + マルチアームバンディット |
| **ガバナンス・公平性** | なし | なし | なし | 手作業チェック | 自動公平性、品質ゲート、監査証跡 |
| **リスク管理** | なし | なし | 限定的 | 定性的 | 定量的（CVaR、ポートフォリオリスク） |
| **透明性** | 高（SQL クエリ） | 低（ブラックボックス） | 中 | 高（スライド） | 高（推定器 + 診断が可視化） |
| **リアルタイム更新** | あり | 場合による | 限定的 | なし | あり – 継続的コンソール |
| **マルチテナント** | 場合による | なし | 場合による | N/A | あり – RLS + RBAC |
| **デプロイモデル** | クラウド SaaS | クラウド SaaS | クラウド SaaS | コンサルプロジェクト | セルフホスト or クラウド（Docker） |
| **コスト構造** | サブスクリプション | サブスクリプション | サブスクリプション | プロジェクト毎課金 | 初期費用 + インフラ |
| **価値実現までの時間** | 数日 | 数週間 | 数週間 | 数ヶ月 | 数日（データ準備後） |
| **最適用途** | パフォーマンス追跡 | リードスコアリング、離脱予測 | キャンペーン最適化 | 戦略的イニシアティブ | 継続的因果マーケティング意思決定 |

**重要なポイント:**

- **BI ダッシュボード**は「何が起きたか」を教えてくれますが、「なぜ」や「何をすべきか」は教えてくれません
- **一般的な AI/ML** は予測を最適化しますが、因果性やビジネス制約を無視します
- **アップリフト SaaS** はスコアリングに焦点を当てていますが、ポートフォリオ・実験・ガバナンスが不足
- **コンサルティングファーム**は深いインサイトを一度提供しますが、継続的な運用システムではありません
- **CQOx** は因果性、ポートフォリオ最適化、実験、ガバナンスを単一の監査可能なセルフサービスプラットフォームに統合

## 4. 主なモジュール

### 4.1 Datasets & Causal Design – データセットと因果デザイン

**目的**：  
アップロードしたデータを、「どの列が何の役割か」まで含めて  
**因果推論にかけられる形** にする。

- CSV アップロード or DWH テーブル参照
- 自動検知するカラムの例：
  - 処置列：`treatment`, `arm`, `variant_a` など
  - 成果列：`revenue`, `sales`, `ltv`, `delta_yen` など金額系
  - ユーザ ID：`user_id`, `customer_id`
  - 時間：`timestamp`, `date`
  - チャネル・セグメント：`channel`, `segment`, `campaign_id`
  - コスト：`cost`, `spend`

**自動検知ロジックのイメージ**（実装は Python 側）：

- カラム名 + 値の種類数 + 分布を見て候補を出す
  - 0/1 だけの列で `treatment` を含む名前 → バイナリ処置候補
  - 値が少数カテゴリ（control / variant_a / variant_b 等）→ 多腕処置候補
  - 正の偏りのある金額列 → 成果候補
  - 高カーディナリティ → ID 候補
- UI 上では「(auto-detected)」ラベル付きでプルダウン表示し、  
  ユーザが変更できるようにする

---

### 4.2 Decision Console – マーケ施策意思決定コンソール

**目的**：
CMO / マーケ責任者が、「今システムがどれだけお金を生んでいて、
どれだけのリスクを取っているか」を **一枚で把握** できる画面。

![Decision Console](Picture/Screenshot%20from%202025-11-27%2016-41-20.png)
*KPIs、Δ¥トレンド、セグメントポートフォリオ、施策カードを一画面で表示*

**メイン KPI カード**

- **Total Incremental Profit (Δ¥)**  
  - 選択期間内の Go（＋必要なら Canary）施策の Δ¥ 合計

- **Average Δ¥ / Policy**  
  - 施策 1 件あたりの平均 Δ¥  
  - 0 以上を目標

- **Mean CAS (Causal Assurance Score)**  
  - 施策ごとの CAS の平均値  
  - Low / Medium / High の 3 区分を表示

- **CVaR (worst 10%)**  
  - Δ¥ 分布の下位 10% の期待値  
  - 「悪い方に振れたとき、どれくらい負ける可能性があるか」

**グラフ & テーブル**（Visualization の仕様）

- **Δ¥ Trend**  
  - X: 週 or 日、Y: Δ¥ 合計  
  - 棒グラフで Δ¥、折れ線で CAS など

- **Segment Portfolio**  
  - バブルチャート  
  - X: セグメント規模（ユーザ数）  
  - Y: ユーザあたり Δ¥  
  - バブルサイズ: Δ¥ 合計  
  - 色: CAS 区分（High / Medium / Low）

- **Channel Performance**  
  - X: チャネル（Email / Push / App / Web など）  
  - 左軸: Δ¥（棒）  
  - 右軸: ROI（折れ線）

- **Decision Cards テーブル**  
  - カラム：`Policy`, `Dataset`, `Channel`, `Segment`, `Δ¥`, `ROI`, `CAS`, `Risk`, `Verdict`, `Period`  
  - フィルタ：Verdict チップ（All / Go / Canary / Hold）、テキスト検索

### 4.3 Portfolio – ポートフォリオ & ROI

**目的**：
「どの施策を組み合わせて走らせるのがベストか」を、
利益・リスク・CAS の観点から決める。

![Portfolio](Picture/Screenshot%20from%202025-11-27%2016-44-03.png)
*パレートフロンティア、貢献度分析、施策選択を含むポートフォリオビュー*

- **Recommended Portfolio Strategy カード**  
  - `Expected Δ¥`, `CAS Score`, `Risk Score`, `ROI`  
  - `Decision Rationale`（文章）と `Recommendations`（箇条書き）

- **Pareto Frontier (Profit vs Risk)**  
  - X: Risk, Y: Profit(Δ¥)  
  - 点の色：CAS（High / Med / Low）  
  - 破線：パレートフロンティア

- **Portfolio Contribution**  
  - Δ¥ 貢献度トップ N 施策の棒グラフ

- **Portfolio Policies テーブル**  
  - カラム：`Policy Name`, `Dataset`, `Channel`, `Δ¥`, `ROI`, `Risk`, `CAS`, `Verdict`, `Tag(Include/Test/Exclude)`

### 6.2 主要アーキテクチャパターン

**1. Row-Level Security (RLS) によるマルチテナンシー**
- PostgreSQL RLS ポリシーがテナント間のデータ分離を保証
- 各 API リクエストは tenant_id を含む JWT で認証
- データベースが認証されたテナントに基づいてクエリを自動フィルタリング

**2. ロールベースアクセス制御 (RBAC)**
- 3 つの主要ロール：`admin`、`analyst`、`viewer`
- API ゲートウェイとデータベースレベルで権限を強制
- Admin：全アクセス；Analyst：読取 + 分析 + エクスポート；Viewer：読取専用

**3. イベント駆動アーキテクチャ**
- 長時間実行タスク（モデル学習、シミュレーション）を非同期実行
- WebSocket/SSE によるフロントエンドへのリアルタイム進捗更新
- ジョブキュー（オプション：Redis/Celery）によるバックグラウンド処理

**4. ステートレス API 設計**
- すべての状態はデータベースまたはクライアント (JWT) に保存
- API ゲートウェイと計算ノードの水平スケーリングを可能に
- JWT トークンによるセッション管理（有効期限設定可能）

**5. 多層防御セキュリティ**
- 転送中の SSL/TLS 暗号化 (Nginx)
- 保存時のデータ暗号化 (PostgreSQL 暗号化)
- JWT 署名検証
- SQL インジェクション防止（パラメータ化クエリ）
- XSS 防止 (React エスケープ + CSP ヘッダ)
- 状態変更操作の CSRF トークン

## 7. API 使用例

CQOx はすべてのコア操作のための包括的な REST API を公開しています。以下は `curl` と Python を使用した例です。

### 7.1 認証

**JWT トークン取得:**

```bash
curl -X POST http://localhost:8000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{
    "email": "admin@cqox.com",
    "password": "your-password"
  }'
```

**レスポンス:**
```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "bearer",
  "expires_in": 3600
}
```

**Python 例:**
```python
import requests

BASE_URL = "http://localhost:8000/api/v1"

# ログイン
response = requests.post(f"{BASE_URL}/auth/login", json={
    "email": "admin@cqox.com",
    "password": "your-password"
})
token = response.json()["access_token"]

# 以降のリクエストでトークンを使用
headers = {"Authorization": f"Bearer {token}"}
```

---

### 7.2 データセットアップロード

**エンドポイント:** `POST /api/v1/datasets`

```bash
curl -X POST http://localhost:8000/api/v1/datasets \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "file=@campaign_data.csv" \
  -F "name=Q4 メールキャンペーン" \
  -F "description=処理割当を含むメールキャンペーン"
```

**Python 例:**
```python
with open("campaign_data.csv", "rb") as f:
    files = {"file": f}
    data = {
        "name": "Q4 メールキャンペーン",
        "description": "処理割当を含むメールキャンペーン"
    }
    response = requests.post(
        f"{BASE_URL}/datasets",
        headers=headers,
        files=files,
        data=data
    )
    dataset_id = response.json()["dataset_id"]
    print(f"データセットアップロード完了: {dataset_id}")
```

## 8. セキュリティ & コンプライアンス

CQOx は、データ保護、アクセス制御、規制遵守を確保するため、エンタープライズグレードのセキュリティとコンプライアンス機能を実装しています。

### 8.1 認証 & 認可

**JWT + OAuth2 認証**
- ステートレス認証のための JSON Web Tokens (JWT)
- エンタープライズ SSO のための OAuth2 統合 (Google、Azure AD、Okta)
- 設定可能なトークン有効期限（デフォルト：1 時間アクセス、7 日間リフレッシュ）
- セキュアなパスワードハッシング（bcrypt with salt）

**ロールベースアクセス制御 (RBAC)**

| ロール | 権限 |
|--------|------|
| **Admin** | システム全体へのアクセス：ユーザ、データセット、ポリシー、設定、エクスポートの管理 |
| **Analyst** | 読取 + データ分析、ポリシー作成、実験実行、結果エクスポート |
| **Viewer** | ダッシュボード、レポート、可視化への読取専用アクセス |

RBAC 強制ポイント：
- API ゲートウェイ（FastAPI 依存関係）
- データベース（PostgreSQL RLS ポリシー）
- フロントエンド（UI コンポーネントの可視性）

### 8.2 データセキュリティ

**暗号化**
- **転送中**: すべてのクライアント・サーバー通信に TLS 1.3
- **保存時**: 機密列（PII、財務データ）の PostgreSQL 暗号化
- **API トークン**: 暗号化ストレージ、ハッシュ比較

**マルチテナンシー & データ分離**
- PostgreSQL の Row-Level Security (RLS) がテナントデータ分離を保証
- 各 API リクエストは tenant_id を含む JWT で認証
- データベースが認証されたテナントに基づいてすべてのクエリを自動フィルタリング
- データベースポリシーによるテナント間データ漏洩防止

### 8.3 ガバナンス & コンプライアンス

**監査証跡**
- すべての重要な操作をログ記録：
  - ユーザ ID、ロール、タイムスタンプ
  - アクション タイプ（create、read、update、delete、export）
  - リソース ID（dataset、policy、experiment）
  - IP アドレス、ユーザエージェント
- 不変監査ログ（追記専用）
- 監査ログ保持期間：7 年（設定可能）

**公平性 & バイアス検出**
- センシティブ属性（性別、年齢、民族等）間の自動公平性チェック
- 統計的パリティ、機会均等、均等化オッズメトリクス
- ポリシーごとの設定可能な公平性閾値
- 自動保留推奨付き違反アラート

**頻度キャップ & 露出制限**
- ユーザごとの接触頻度制限（例：週最大 3 通のメール）
- キャンペーンごとの露出上限
- チャネル固有の制限（Email、Push、SMS 等）
- ガバナンスセンターでコンプライアンス違反を自動フラグ

**品質ゲート**
- 最小サンプルサイズ要件
- CAS 閾値強制（例：CAS < 0.4 のポリシーをブロック）
- データ品質チェック（欠損値、外れ値、データドリフト）
- 設定可能な重大度レベル：`info`、`warning`、`critical`
- 重大違反での自動ブロック

**規制コンプライアンス**
- **GDPR**: アクセス権、削除権、データポータビリティ、同意管理
- **CCPA**: データ開示、オプトアウトメカニズム、非差別
- **SOC 2**: セキュリティ制御、アクセスログ、暗号化
- **HIPAA** (オプション): PHI 暗号化、アクセス制御（医療クライアント向け）

### 8.4 セキュリティベストプラクティス

**本番環境のデプロイ推奨事項:**
1. **本番環境**:
   - HTTPS のみ使用（Let's Encrypt または企業証明書付き Nginx）
   - ファイアウォールルール有効化（ポート 80/443 のみ許可）
   - プライベートネットワーク上でデータベースを分離
   - シークレット管理を使用（Vault、AWS Secrets Manager）

2. **データベースセキュリティ**:
   - 強力なパスワード（16 文字以上、四半期ごとにローテーション）
   - パブリックアクセス無効化（localhost または プライベート IP にバインド）
   - PostgreSQL SSL 接続有効化
   - 定期的なバックアップ（日次フル + 時間毎増分）

3. **API セキュリティ**:
   - レート制限（ユーザあたり 100 req/min、テナントあたり 1000 req/min）
   - CORS ホワイトリスト（許可オリジンを制限）
   - 入力検証（Pydantic スキーマ）
   - SQL インジェクション防止（パラメータ化クエリのみ）

4. **監視 & インシデント対応**:
   - ログイン失敗試行のリアルタイムアラート（10 分間に 5 回以上）
   - 異常検知（異常なデータアクセスパターン）
   - インシデント対応プレイブック
   - 定期的なセキュリティ監査 & ペネトレーションテスト
