# CQOx – 因果マーケティング意思決定プラットフォーム

**📖 Documentation**
[🏠 README (Quick Start)](README.md) | [🇺🇸 English (Full)](README_en.md) | **🇯🇵 日本語 (Full)**

---

**CQOx（シーキューオーエックス）** は、  
マーケティング施策の **因果効果** と **利益・リスク・公平性** を一枚のコンソールにまとめるためのプラットフォームです。

- 生のイベントデータ（CSV やテーブル抽出）から  
  **インクリメンタル利益（Δ¥）** と **リスク** を推定し、
- 「実行すべき施策（Go）」「慎重にテストすべき施策（Canary）」「止めるべき施策（Hold）」を提示し、
- その裏側で **因果推論・実験・ポートフォリオ最適化・ガバナンス（公平性や頻度上限）** を自動で回します。

> 一言で言うと：「Google / Netflix / Meta / WPP / BCG のトップチームが  
> 内製している “因果ベースの意思決定コンソール” を、  
> 一般企業でも使える形に落とし込んだもの」です。

---

## 1. なぜ CQOx が必要か

多くのツールはここで止まります：

- **見た目のダッシュボード**：CVR、売上、開封率など「起きたこと」のグラフ
- **ブラックボックスなスコア**：「購入確率 0.83」などの機械学習スコア

しかし、経営・マーケの現場で本当に聞かれるのは次のような問いです。

- 「このセグメントに、この施策を打ったとき、  
  **どれだけ利益が増えた（Δ¥）と言えるのか？**」
- 「どれくらいの **リスク** を取っているのか？最悪どこまで赤字になりうるのか？」
- 「この施策ポートフォリオで、  
  予算・リスク・公平性の制約を守りながら、成長を最大化できているか？」

Google / Meta / Netflix / Amazon、そして WPP / BCG / Accenture などのコンサルは、  
社内で次の 4 つを組み合わせたスタックを持っています。

1. **因果推論**（uplift、DiD、IV、RD、SCM など）
2. **実験プラットフォーム**（A/B テスト、多腕バンディット）
3. **ポートフォリオ最適化**（利益 vs リスク、CVaR）
4. **ガバナンス**（公平性・頻度キャップ・品質ゲート）

CQOx は、これらのパターンを 1 つのプロダクトにまとめたものです。

## 2. CSV から意思決定までのストーリー

典型的な利用フローはこうなります。

1. **データをアップロード**  
   - 例：キャンペーンログ、ユーザ単位の成果、属性、コスト情報

2. **因果デザインの設定（Causal Design）**  
   - アップロードしたカラムから、  
     **処置列（treatment）・成果列（outcome）・ユーザ ID・時間・チャネル・コスト** 候補を自動検知
   - ユーザが画面上で最終的な列を確認・修正
   - 使用する推定器（DR, IPW, DiD, IV, CF, SCM, RD など）を選択

3. **因果モデルの学習と診断**  
   - 複数の推定器を並列に学習し、  
     オーバーラップ・バランス・感度分析を実行
   - その結果をまとめて **Causal Assurance Score (CAS)** としてスコアリング

4. **Decision Console – マーケ意思決定コンソール**  
   - 実行候補の施策（Policy）を集約し、  
     期間内の **総インクリメンタル利益（Δ¥）・平均 Δ¥ / 施策・平均 CAS・テイルリスク(CVaR)** を一枚で表示
   - セグメント別・チャネル別に Drill-down 可能

5. **Portfolio – ポートフォリオ最適化 & ROI**  
   - 各施策を **利益 vs リスク vs CAS** の多目的パレートフロンティア上にプロット
   - 「どの施策をポートフォリオに含めるべきか」を提案

6. **Digital Twin – 顧客デジタルツイン**  
   - ペルソナごとに、プレミアム施策 / 値引き / ナーチャリング / リテンション施策を当てた場合の  
     反応と Δ¥ をシミュレーション

7. **Experiment Studio – オンライン・マルチアーム実験**  
   - 実際のトラフィックを使ったオンライン実験（A/B, 多腕バンディット）の設計・運用
   - 過去データを使ったマルチアーム因果分析

8. **Governance Center – 公平性・品質・コンプライアンス**  
   - 性別・年齢などの **センシティブ属性ごとの Δ¥ 差** をチェック
   - uplift 入力データの品質検査
   - **頻度キャップ・露出上限** の違反を検出し、ログを記録

9. **Export Gate**  
   - 承認されたセグメントや施策ポリシーを、  
     外部の ESP / CDP / マーケ自動化ツールにエクスポート

## 3. CQOx は何が違うのか

### 3.1 BI ダッシュボードとの違い

- BI は「起きたこと（売上、CVR）」をきれいに見せるツールです。
- CQOx は「施策を打った **結果として** どれだけ変わったか（Δ¥）」を推定し、  
  さらに「もし施策を変えたらどう変わりそうか」をシミュレーションします。

ポイント：

- すべてのビューの中心が **インクリメンタル利益（Δ¥）**  
  純売上ではなく「やったから増えた分」だけを見る。
- **施策単位（Policy 単位）** での分析が基本  
  （例：「App 有りの RFM4–5 に Push V3 を 3 通送る」など）
- すべての数字に **CAS（因果保証スコア）** と **リスク指標** が紐づく

### 3.2 一般的な AI / 機械学習ツールとの違い

よくある「AI マーケ支援ツール」は次のような動きをします。

- 「購入確率」「離脱確率」などの **予測モデル** を作る
- **AUC や logloss** など、統計的な損失関数を最小化するように学習する
- 予測スコアをそのまま「スコアが高い人＝狙い目」と解釈する

これに対して、CQOx は性質がまったく違います。

- **予測ではなく「もし〜していなかったら？」を扱う（因果）**  
  - AI は「今の情報を見て、この人は買いそうか？」という **予測** をします。  
  - CQOx は「この人に施策を送った場合と、送らなかった場合で、  
    **どれだけ売上が変わるか？**」という **反事実（カウンターファクト）** を推定します。  
  - そのために、推定器・仮定・診断がすべて明示されています。

- **指標は AUC ではなく、利益・リスク・公平性**  
  - 目的は「Δ¥ を最大化しつつ、リスクと不公平性を抑える」ことです。  
  - クリック数や CVR が上がっても、**増分利益がマイナス** なら「悪い施策」と判断されます。

- **ブラックボックスではなく、監査可能な仕組み**  
  - DR / IPW / DiD / IV / CF / SCM / RD などの推定器が UI から見えます。  
  - バランスチェック・オーバーラップ・感度分析も画面で確認できます。  
  - 「なぜこの施策が Go 判定なのか？」を、データサイエンティストがトレースできます。

- **時間が経っても壊れにくい**  
  - 単純な予測モデルは、データ分布が変わるとすぐ壊れます。  
  - CQOx は「施策の効果」を推定しているため、  
    特定のチャネルやセグメントが多少変化しても、**方針（ポリシー）自体は比較的安定** しやすい設計です。

一言でまとめると：

> 一般的な AI は「パターンを当てる」のが得意。  
> CQOx は「施策の **影響** を推定し、  
> その結果を利益とリスクの観点で **意思決定に落とし込む**」ことに特化しています。

### 3.3 uplift SaaS / コンサルティングとの違い

- コンサルティングファームは、  
  「一度きりの分析結果をまとめたスライド（戦略提案書）」を提供することが多いです。  
  CQOx は、これを **毎週 / 毎日回せる “コンソール” として常設** します。

- uplift 専用 SaaS は、スコアリングまでは強い一方で、  
  ポートフォリオ・ガバナンス・実験プラットフォームまでは踏み込まないことが多いです。  
  CQOx はこれらを **一つのワークフローに統合** している点が違います。

### 3.4 CQOx は AI をどう使い、何を任せないのか

CQOx 自体は「全部を AI に丸投げするツール」ではありません。  
AI（特に大規模言語モデル）は **サポート役** にとどめ、  
**意思決定の根拠は必ず因果推論とルール（ガバナンス）側に保持** します。

AI を使うのは、たとえばこんな場面です。

- ポートフォリオの推奨結果を、人が読みやすい文章で要約する  
  （例：「この 5 施策を採用すると、Δ¥ は約 66 万円、リスクは中程度、CAS は 0.75 です…」）
- セグメント説明やペルソナ説明文を自動生成する  
- Diagnostics の結果を「どこに注意すべきか」ハイライトする

逆に、AI に **任せない** のは次の部分です。

- 因果効果の推定そのもの（これは統計・因果推論のエンジンが担当）
- ガバナンスルール（公平性・頻度キャップ・品質ゲート）の判定
- 人間による最終承認なしに、勝手に施策を配信すること

この設計により、

- 「AI がなぜこう判断したのかわからない」状態を避けられ、
- 監査・再現性・コンプライアンスに耐えられる形で  
  AI の便利さだけを取り込むことができます。

## 4. 主なモジュール

ここからは英語版と同じ構成を日本語で要約します。  
詳細な UI 仕様（どのカードに何を表示するか）は、  
プロダクトオーナー向けの仕様としても使えるように書いています。

### 4.1 Datasets & Causal Design – データセットと因果デザイン

**目的**：  
アップロードしたデータを、「どの列が何の役割か」まで含めて  
**因果推論にかけられる形** にする。

- CSV アップロード or DWH テーブル参照
- 自動検知するカラムの例：
  - 処置列：`treatment`, `arm`, `variant_a` など
  - 成果列：`revenue`, `sales`, `ltv`, `delta_yen` など金額系
  - ユーザ ID：`user_id`, `customer_id`
  - 時間：`timestamp`, `date`
  - チャネル・セグメント：`channel`, `segment`, `campaign_id`
  - コスト：`cost`, `spend`

**自動検知ロジックのイメージ**（実装は Python 側）：

- カラム名 + 値の種類数 + 分布を見て候補を出す
  - 0/1 だけの列で `treatment` を含む名前 → バイナリ処置候補
  - 値が少数カテゴリ（control / variant_a / variant_b 等）→ 多腕処置候補
  - 正の偏りのある金額列 → 成果候補
  - 高カーディナリティ → ID 候補
- UI 上では「(auto-detected)」ラベル付きでプルダウン表示し、  
  ユーザが変更できるようにする

---

### 4.2 Decision Console – マーケ施策意思決定コンソール

**目的**：
CMO / マーケ責任者が、「今システムがどれだけお金を生んでいて、
どれだけのリスクを取っているか」を **一枚で把握** できる画面。

![Decision Console](Picture/Screenshot%20from%202025-11-27%2016-41-20.png)
*KPIs、Δ¥トレンド、セグメントポートフォリオ、施策カードを一画面で表示*

**メイン KPI カード**

- **Total Incremental Profit (Δ¥)**  
  - 選択期間内の Go（＋必要なら Canary）施策の Δ¥ 合計

- **Average Δ¥ / Policy**  
  - 施策 1 件あたりの平均 Δ¥  
  - 0 以上を目標

- **Mean CAS (Causal Assurance Score)**  
  - 施策ごとの CAS の平均値  
  - Low / Medium / High の 3 区分を表示

- **CVaR (worst 10%)**  
  - Δ¥ 分布の下位 10% の期待値  
  - 「悪い方に振れたとき、どれくらい負ける可能性があるか」

**グラフ & テーブル**（Visualization の仕様）

- **Δ¥ Trend**  
  - X: 週 or 日、Y: Δ¥ 合計  
  - 棒グラフで Δ¥、折れ線で CAS など

- **Segment Portfolio**  
  - バブルチャート  
  - X: セグメント規模（ユーザ数）  
  - Y: ユーザあたり Δ¥  
  - バブルサイズ: Δ¥ 合計  
  - 色: CAS 区分（High / Medium / Low）

- **Channel Performance**  
  - X: チャネル（Email / Push / App / Web など）  
  - 左軸: Δ¥（棒）  
  - 右軸: ROI（折れ線）

- **Decision Cards テーブル**  
  - カラム：`Policy`, `Dataset`, `Channel`, `Segment`, `Δ¥`, `ROI`, `CAS`, `Risk`, `Verdict`, `Period`  
  - フィルタ：Verdict チップ（All / Go / Canary / Hold）、テキスト検索

---

### 4.3 Portfolio – ポートフォリオ & ROI

**目的**：
「どの施策を組み合わせて走らせるのがベストか」を、
利益・リスク・CAS の観点から決める。

![Portfolio](Picture/Screenshot%20from%202025-11-27%2016-44-03.png)
*パレートフロンティア、貢献度分析、施策選択を含むポートフォリオビュー*

- **Recommended Portfolio Strategy カード**  
  - `Expected Δ¥`, `CAS Score`, `Risk Score`, `ROI`  
  - `Decision Rationale`（文章）と `Recommendations`（箇条書き）

- **Pareto Frontier (Profit vs Risk)**  
  - X: Risk, Y: Profit(Δ¥)  
  - 点の色：CAS（High / Med / Low）  
  - 破線：パレートフロンティア

- **Portfolio Contribution**  
  - Δ¥ 貢献度トップ N 施策の棒グラフ

- **Portfolio Policies テーブル**  
  - カラム：`Policy Name`, `Dataset`, `Channel`, `Δ¥`, `ROI`, `Risk`, `CAS`, `Verdict`, `Tag(Include/Test/Exclude)`  
  - Include / Test / Exclude を変更するとポートフォリオ推奨が更新される

---

### 4.4 Digital Twin – 顧客デジタルツイン

**目的**：
「このペルソナに対して施策を変えたら、どんな結果になりそうか？」を、
本番配信前に検証する。

![Digital Twin](Picture/Screenshot%20from%202025-11-27%2016-46-06.png)
*ペルソナカードとシナリオシミュレーション画面*

- ペルソナカード（年齢レンジ / LTV / 購買頻度 / 収入レンジ / 一言説明）
- シナリオカード（メール頻度 / 割引率 / パーソナライズ度などのパラメタ）
- 「Run Simulation」ボタンで、ペルソナ × シナリオ の Δ¥ とリスクを表示

---

### 4.5 Experiment Studio – 実験スタジオ

**目的**：
オンライン実験（A/B、多腕バンディット）と、
オフラインのマルチアーム因果分析を一元管理する。

![Experiment Studio](Picture/Screenshot%20from%202025-11-27%2016-47-53.png)
*マルチアーム実験のオーケストレーションとアロケーション画面*

- Experiment Orchestrator（実験名・指標・アームの設定）
- Online Experiments 一覧（状態・Allocation 確認ボタン）
- Update Outcomes JSON（`{arm_id, reward}` の配列）で結果を反映
- Multi-Arm Experiment Setup（`treatment_arm`, `delta_yen` などの列指定）
- Offline Analysis JSON（`X`, `T`, `Y`）で過去データ解析

---

### 4.6 Governance Center – ガバナンスセンター

**目的**：
施策が配信される前に、
**公平性・品質・頻度キャップ** の観点から安全性を検証する。

![Governance Center](Picture/Screenshot%20from%202025-11-27%2016-48-28.png)
*公平性チェック、データ品質、コンプライアンス監視を含むガバナンスセンター*

- Data & Sensitivity  
  - Fairness Threshold (Δ¥), Min Samples Required  
  - Sensitive Attributes JSON（性別・年齢レンジなど）  
  - Uplift Data JSON（ユーザごとの Δ¥ と属性）  
  - 「Check Fairness」「Check Data Quality」ボタン

- Compliance (Frequency Cap)  
  - User Exposure JSON（ユーザごとの接触回数）  
  - Max Frequency Cap（上限接触回数）  
  - 「Check Compliance」ボタン

- Quality Gates Overview / Violation Log  
  - ルール一覧と、違反ログの時系列表示

## 6. アーキテクチャ（概要）

- フロントエンド：React + Vite + TanStack Query（ポート 3004）
- API Gateway：FastAPI（ポート 8000）
- Causal Engine：Python サービス（因果推論・診断・シミュレーション）
- Reverse Proxy：Nginx（フロント + API + SSE/WebSocket のゲートウェイ）
- Monitoring：Prometheus + Grafana

すべて Docker 化されており、`docker compose up` で一括起動できます。
